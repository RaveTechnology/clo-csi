# Полный csi-sanity на rc.2 — 19.11.2026

**Production: NO-GO.** Полный набор в штатной конфигурации завершён за
48.824 мин: **50 passed / 2 failed / 50 skipped / 1 pending**, всего 103
спецификации. Ручных focus/skip-фильтров и fail-fast не было.

Проверен опубликованный **CSI 0.1.0-rc.2**.
До и после прогона сверены digest образа и SHA-256 бинарников controller/node;
pod UID сохранились, перезапусков driver-контейнеров не было. Стенд — одна
приватная RKE2-нода 2 shared CPU / 8 ГБ / boot 30 ГБ с временным NAT.
Тестовый бинарник собран из исходников этого выпуска: изменён только защитный
project placeholder на ID собственного стенда. Тесты и их ожидания не менялись.

## Две ошибки расширения

- `Node Service / NodeExpandVolume / should work if node-expand is called after node-publish`.
- `ExpandVolume [Controller Server] / should work`.

В обоих случаях upstream сначала создаёт **свежий свободный том** и вызывает
ControllerExpandVolume 10→12 ГиБ. В первом тесте это происходит до подключения,
несмотря на название сценария. CLO возвращает том в `ERROR`, сообщает размер
12 ГиБ; attachment отсутствует. CSI возвращает FailedPrecondition и сохраняет
отправленную операцию как Uncertain. В реестре каждого тома одна sent extend;
отдельной полной HTTP-трассировки всех запросов не было.

Оба сценария также имеют дополнительную ошибку AfterEach: удаление через CSI
блокируется незавершённым расширением. Это две дополнительные ошибки очистки
внутри тех же двух спецификаций. Статус операции вручную не сбрасывался.

Расширение подключённых RWO/ext4 PVC 10→12 ГиБ прошло три отдельные проверки,
включая точный rc.2. Сохранность данных и повторное подключение описаны
в [отдельном отчёте](attached-resize-2026-11-19.md).

## Что пропущено

Из 50 skipped **49 относятся к неподдерживаемым возможностям**, один — к
`testnodevolumeattachlimit`, выключенному в upstream по умолчанию. Проверка
девятого подключения в этом прогоне не включалась; лимит восьми дисков здесь
заново не квалифицирован. Единственный pending — upstream-тест ListVolumes
pagination. Все причины пропусков приведены в [JSON](full-sanity-2026-11-19.json).
HA, перенос между нодами, fencing, нагрузка и SLA этим прогоном не проверялись.

## Очистка и границы проверки

Все 19 native ID созданных дисков проверены как отсутствующие,
включая два оставшихся ERROR-диска. Тестовые VM/boot и NAT удалены. Перед
удалением использовались точные ID из registry и завершённых create operations,
а проект подтверждался полным scoped inventory: detail диска не содержит
поля проекта. Поиск и удаление только по имени не применялись.

Отдельная свежая проверка подтвердила 404 и исходный состав проекта:

2 CPU / 8 ГБ / boot 60 ГБ, его protected UID/credential, HTTPS и резервный IPv4
сохранены. Временный runner и собственный каталог на management-сервере удалены.

прогоном не менялись. Боевые данные, приложения, DNS и телефония не затронуты;
